# Харнес

Выбран upstream Codex 0.159.3, commit `01fc69f4026735edfdf6789820549727a4867b11`, Rust toolchain 1.95.0. Собственный Python-код адаптирует штатный `app-server`; агентный цикл не переписан. Подтверждены ARM64 source-build, отдельные нативные mock-сценарии, короткий live-прогон и один полный набор Luna 5/5. Полный offline-набор, атаки на сборщик и итоговое ревью также завершены; доказательства перечислены в [отчёте](report.md).

Настройки не наследуют личный каталог Codex. В окружение агентной команды разрешены только заданные PATH/HOME; inference- и управляющие токены остаются в доверенной части. `externalSandbox` полагается на Docker-ограничения; выбор среды задаётся отдельно через `environments.toml` и `include_local=false`. Нативные проверки сравнивают маркеры двух сред, независимо читают правку и отключают exec-server, проверяя отсутствие локального исполнения. Состояние этих проверок указано в отчёте.

Для mock-профилей и Luna общий Python-хелпер `sandbox_model` создаёт `model_catalog_json` в каталоге попытки. Он сохраняет исходный `slug`, задаёт `tool_mode=direct`, `shell_type=unified_exec`, `apply_patch_tool_type=freeform`, `use_responses_lite=false`, `node_repl_disabled=true` и короткую инструкцию стенда. Это штатные поля конфигурации Codex 0.159.3: [выбор ToolMode](https://github.com/openai/codex/blob/01fc69f4026735edfdf6789820549727a4867b11/codex-rs/core/src/tools/mod.rs) учитывает метаданные модели, а клиент формирует обычный Responses-запрос с инструкцией и инструментами. Отдельный Node runtime не используется; состав четырёх основных сервисов сохраняется.

Диалог Luna с исходным каталогом завершился без инструментов и файлов и не прошёл чекер; отрицательный исход сохранён в отчёте. После настройки прямого режима прошли [короткая проверка](../results/live-check-20261106T211931Z-0a10fa/summary.json) и [полный набор B1.1–B5.1](../results/d72a5329d7aa4117bb41aa7995be74c9/report.json): реальные инструменты, полные копии, пройденные чекеры и успешная очистка.

Gateway устойчиво принимает fingerprint запроса до provision. Менеджер восстанавливает handle по run id, не повторяя команду. После исполнения доверенный сборщик прекращает запись процессов агента и читает ограниченную стабильную копию до удаления сандбокса. Полнота файлов и нативных доказательств учитывается отдельно; доверенный чекер работает уже на стороне раннера.

Перед запуском app-server harness записывает приватный nonce попытки и передаёт его только своим процессам. Очистка проверяет сессию, UID, исполняемый файл и маркеры; relay может иметь другой PGID. Нативный итог записывается до удаления CODEX_HOME, а подтверждение освобождения — после очистки. После аварии сохранённый итог возвращается без replay; незавершённая попытка получает `interrupted`. Неизвестная принадлежность процесса или неподтверждённая очистка блокирует новый запуск.

Учёт токенов сосредоточен в [budget.py](../services/llm_proxy/budget.py). Mock резервирует точную верхнюю границу искусственных токенов до запроса. Luna использует согласованный `observed_usage`: цель 30 000 входных и выходных токенов, остановка между запросами, допустимое превышение последним запросом. Прокси добавляет `max_output_tokens=2048`; фактический расход сохраняется без обрезки с признаком `over_target`. При неизвестном usage следующие запросы блокируются. Разовые проверки endpoint завершены; рабочий профиль не зависит от экспериментальных скриптов или имён их отчётов.

В `observed_usage` поле `reserved` обозначает только выходной cap незавершённого запроса; доказанной границы входа у него нет. Естественно завершившаяся задача может иметь `over_target=true`. `budget_exceeded` возникает, когда требуется следующий запрос после достижения цели. Для строгого mock проверяется сумма подтверждённого расхода и полного резерва входа/выхода.

Выделенная авторизация хранится в `.auth/`, исключённом из Git и Docker context. Первичный device-login выполняется явной командой из README. В live Compose harness владеет записью и удерживает `flock`, llm-proxy читает тот же bind-mount без права записи; менеджер и агент не получают его.

Свежий access token проходит локальную проверку срока. Для обновления создаётся отдельный чистый CODEX_HOME только с auth.json и служебными настройками. Auth-only Codex вызывает закреплённый `getAuthStatus(includeToken=false, refreshToken=true)` без диалога и генерации. Его refresh идёт через loopback-мост владельца и узкий маршрут llm-proxy к `https://auth.openai.com/oauth/token`. До отправки сохраняется намерение ротации; grant, публичный client id и refresh token сверяются с активной попыткой. Ответ передаётся в нативном формате, без redirect и replay.

Новый auth.json становится текущим после подтверждения нативного сохранения и остановки процессов. При аварии подтверждённое локальное обновление восстанавливается; неопределённая ротация сохраняет каталог и блокирует последующую работу до восстановления авторизации. Готовность авторизации и освобождение auth-worker — разные состояния: `wait_idle` подтверждает последнее перед завершением агентного прогона. Проверки с вымышленными credentials и фактическая live-ротация перечисляются отдельно в отчёте.

Нативная ротация через Compose подтверждена отдельной [проверкой авторизации](../results/live-check-20261106T211035Z-24118a/auth.json). Доказательство refresh-маршрута и сохранения credentials отделено от отчёта пяти агентных задач.

Ресурсные потолки: одна vCPU, один CPU worker, до 8 000 000 000 байт RAM. Builder ограничен 7 ГБ и выполняется отдельно от стека. `docker/compose.single-cpu.yml` допускается после `preflight --shared-cpu`, который проверяет одну vCPU всего Docker engine; лимит каждого сервиса в этом режиме не является дополнительным CPU.

Для текущего Docker Desktop выделены 32 ГБ диска. Учёт включает toolchain, зависимости, кэш, образы, исходники, Python-окружение, временные копии и историю. Это настройка ёмкости Docker, не обещание свободного места. Материализованные резервы `Storage` защищают место для итогов в прикладной области; отдельная жёсткая квота проекта не задаётся. История и чужие ресурсы не удаляются автоматически ради освобождения места.

Удаление сандбокса не удаляет историю run id. Явное удаление серверной истории оператором завершает гарантию идемпотентности для удалённых id. После аварии незавершённый прогон не переисполняется. Ошибка очистки блокирует следующий запуск. Обычные `down` и `down -v` проверены на реальных контейнерах: собственные среды удаляются, чужие ресурсы и выгруженные результаты сохраняются. `.auth/` хранится вне удаляемых томов.
