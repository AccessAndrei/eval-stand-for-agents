# Контракты

| Файл | Протокол |
|---|---|
| [v0.schema.json](v0.schema.json) | запуск, состояние, события, результат, артефакты, отчёт раннера и управление средой |
| [mounted.schema.json](mounted.schema.json) | v1 сессии, запуск в смонтированном `/work`, события, управление исполнителем и сбор метаданных |
| [validation.py](validation.py) | проверка схем и согласованности независимых исходов, токенов и доказательств |

JSON Schema `v0` описывает управляющие сообщения и результаты. Для проверки
выбирается `$ref` нужного определения.

| Направление | Определения `v0.schema.json#/$defs/…` |
|---|---|
| Раннер ↔ gateway | `launch`, `status`, `event`, `result`, `cancel` |
| Управляющая часть ↔ sandbox-manager | `provision`, `lookup`, `collect`, `release`, `manager_cancel`, `connect`, `manager_status` |
| Итоговый отчёт и доказательства | `report`, `evidence`, `command_event` |

Команды харнесса передаются в сандбокс по нативному протоколу Codex exec-server
через аутентифицированный CONNECT. `command_event` описывает собранное
доказательство вызова.

| Направление v1 | Операции |
|---|---|
| Клиент ↔ Gateway | `/v1/sessions`, регистрация туннеля, монтирование, закрытие, `/runs`, статус, NDJSON-события с курсором и отмена |
| Харнес ↔ Sandbox Manager | Подготовка среды, резерв запуска, аутентифицированный CONNECT, сбор метаданных и освобождение среды |
| CONNECT ↔ Codex exec-server | `process/start` для RunCommand, `fs/readFile` для ReadFile, `fs/writeFile` для WriteFile |

В v1 клиент создаёт идентификатор сессии и предъявляет подтверждение владения
в `X-Session-Proof`. Сервер хранит его хеш. Файлы доступны агенту через
смонтированный `/work`. Терминальное событие `result` содержит отдельные исходы
исполнения и сбора с подтверждением остановки писателей.

Результат отдельно фиксирует исполнение, сбор, очистку и ошибки по стадиям.
Чекер оценивает только полную независимую копию. Учёт токенов указывает режим
`strict` или `observed_usage`, фактический расход либо причину его неизвестности.
Поведение описано в [документации харнесса](../docs/harness.md).

`task_id` содержит от 1 до 64 символов ASCII. Первый символ является
буквой или цифрой. Далее допустимы буквы, цифры, точка, дефис и подчёркивание.
Определение используется для задач датасета и сообщений v0. Отчёт содержит
непустой список строк с уникальными `task_id` в порядке датасета, включая
незапущенные задачи. Валидатор сверяет счётчики и итог со строками отчёта.
Размер файла отчёта ограничивает дисковый бюджет раннера.

Схема исходов исполнения различает `command_error`, `timeout`,
`sandbox_error` и `transport_error`. Ошибку команды харнесс может обработать
внутри текущего turn; таймаут команды или turn завершает текущую попытку.
Ошибки сандбокса и транспорта завершают попытку без повторного исполнения команды.
Автоматического перезапуска попытки нет; повтор запуска с тем же run id
и содержимым получает сохранённое состояние. Политика восстановления описана
в [ADR-0004](../docs/adr/0004-run-lifecycle.md).
